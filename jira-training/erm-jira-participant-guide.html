Jira for the ERM Team

Project: Enterprise Risk Management (ERM)  ·  Platform: Jira Cloud  ·  Version: 1.0

Overview

Jira is the ERM team's system of record for tracking work across all levels of the project portfolio. It is not a sprint board or an agile tool — it is a structured way to capture, assign, and monitor work items from large multi-month initiatives down to individual deliverables.

We do not use story points, velocity, or sprint ceremonies. All work is tracked against dates and explicit status transitions.

Jira ticket IDs in the ERM project follow the format ERM-001, incrementing automatically when a new item is created.

Work Hierarchy

Every piece of work in the ERM project belongs to one of three levels. The levels are strictly nested: Stories roll up to Features, Features roll up to Epics.

Epic
A major strategic initiative. Contains multiple Features.
6 – 12 months
Feature
A significant deliverable within an Epic. Contains multiple Stories.
1 – 3 months
Story
A discrete, assignable unit of work. The primary day-to-day item.
1 – 3 weeks
When in doubt about where something belongs, ask: could one person complete this in under three weeks? If yes, it is a Story. If it spans months and has multiple sub-deliverables, it is a Feature or Epic.

Epics

Epics represent the largest unit of tracked work. They are typically aligned to an annual or strategic program goal. In Jira Cloud, Epics are created the same way as other issue types — by selecting Epic in the issue type dropdown when creating a new item.

Key fields for Epics

FieldNotesRequired
Title (Epic Name)Short, descriptive. Should name the initiative, not the outcome.Required
DescriptionScope boundaries, background, and stakeholder context.Required
AssigneeThe person accountable for the Epic's overall progress.Required
Start Date / Due DateSet at Epic level to bound the initiative window.Required
PriorityCritical / High / Medium / LowOptional

Features

Features are the major deliverables within an Epic. A Feature should produce a tangible output — a report, a process, a policy, a tool — that can be independently reviewed or handed off. Each Feature must be linked to a parent Epic.

Key fields for Features

FieldNotesRequired
TitleName the deliverable, not the activity. e.g. "Risk Appetite Statement" not "Work on risk appetite."Required
DescriptionWhat this Feature produces and what is explicitly out of scope.Required
Parent EpicSet when creating or via the link field.Required
AssigneeDRI for the Feature.Required
Start Date / Due DateShould fall within the parent Epic's date range.Required

Stories

Stories are the primary working unit. They represent a discrete task that a single person can own and complete within one to three weeks. Most day-to-day Jira activity happens at the Story level.

All Story fields

FieldNotesRequired
TitleAction-oriented. Who does what. e.g. "Draft Q3 Risk Register updates for board review."Required
DescriptionContext, background, and any relevant links or reference documents.Required
Acceptance CriteriaSpecific, verifiable conditions that define "done." Use a checklist or numbered list. This is what a reviewer uses to sign off.Required
AssigneeThe person doing the work. Only one assignee per Story.Required
ReporterThe stakeholder who requested or owns the outcome. May differ from Assignee.Required
PriorityCritical / High / Medium / Low. Set relative to other open Stories.Required
Start DateWhen work is expected to begin.Required
Due DateHard deadline, if one exists.Optional
Target End DateWorking estimate for completion. Separate from a hard due date.Required
Parent FeatureLink to the Feature this Story belongs to.Required

Writing good acceptance criteria

Acceptance criteria should answer: how will we know this is done? Each criterion should be verifiable — either it is met or it is not.

Example:
Story: "Update ERM Risk Register for Q3 reporting cycle."

Acceptance Criteria:
1. All 12 risk categories reviewed and residual ratings updated.
2. Control effectiveness ratings updated for any changed controls.
3. Document reviewed and approved by Risk Manager before board submission date.
4. Completed register uploaded to the designated SharePoint folder.

Linking Items

The hierarchy only works if items are connected. There are two ways to establish a parent-child relationship in Jira Cloud.

At creation (preferred)

When creating a Story or Feature, look for the Parent field in the create dialog.
Start typing the Epic or Feature name. Jira will auto-suggest matching items.
Select the correct parent. The link is established on save.

After creation (re-linking)

Open the Story or Feature you want to re-link.
Find the Parent field in the right-hand detail panel.
Click to edit and search for the correct parent item.
Do not use the generic "Link" button to establish parent-child relationships — that creates a peer-level issue link, not a hierarchy link. Use the Parent field specifically.

Views & Navigation

Jira Cloud offers several views of the same data. Use the one that fits the task.

Board view

A column-based view organized by status. Best for seeing what is actively in progress across the team. Not a sprint board — all open work is visible regardless of dates.

Backlog view

A flat list of all Stories not yet started. Good for planning and prioritization. Use this to find work that hasn't been picked up yet.

List view

A tabular view of all items. Best for bulk-reviewing fields, sorting by date, or finding specific tickets quickly. Toggle columns to show only the fields you need.

Finding your work

Use the search bar at the top of Jira (G then G to focus it quickly).
Type your name or ERM- plus a ticket number to jump directly to an item.
Use the My Work section in the left sidebar to see everything assigned to you across projects.

Plans

Jira Plans is a timeline-based view that displays your full work hierarchy — Epics, Features, and Stories — plotted against dates on a Gantt-style chart. It is the most useful view for understanding how work fits together over time and where the team's capacity is concentrated.

Access Plans from the left sidebar under Plans, or from the project's top navigation. The ERM plan is pre-configured to pull from the ERM project.

What Plans shows that other views don't: the relationship between all three levels of the hierarchy on a single timeline. You can collapse Epics to see the high-level roadmap, or expand them to see individual Stories plotted against their start and target end dates.

Key things to know

FeatureHow to use it
Hierarchy levelsUse the Hierarchy toggle at the top to switch between Epic-only, Epic + Feature, or full detail views. Start at Epic level to orient yourself, then drill down.
Date barsEach item's bar is driven by its Start Date and Target End Date in Jira. If a bar is missing or mis-sized, the underlying ticket is missing one of those fields.
DependenciesIf work items are linked as blockers, Plans can display dependency arrows between them. Useful for sequencing work that has hard ordering requirements.
Colour byUse the Colour by option to shade items by Assignee or Priority — helpful for spotting workload concentration at a glance.
Zoom levelSwitch between weeks, months, and quarters using the zoom control in the upper right. Quarters is the most useful default for Epic-level planning.
Saving changesYou can drag and reschedule items directly on the timeline. Changes write back to the underlying ticket's dates immediately. Do not reschedule other people's work without coordinating first.
Plans writes changes directly to live tickets with no confirmation step. Treat it as a read-and-orient tool by default. Only edit on the timeline if you own the item or have explicit permission from the Assignee.

Workflow & Status

Every Story moves through a defined set of statuses. You are responsible for keeping your own tickets current — status should reflect reality, not intent.

To Do In Progress In Review Done
StatusMeaningWho transitions
To DoWork is scoped and assigned but not yet started.Assignee, when starting
In ProgressActive work is underway. Move here the day you begin, not after.Assignee
In ReviewWork is complete and awaiting stakeholder or peer review.Assignee
DoneAcceptance criteria met and confirmed. No further action needed.Assignee or Reviewer

Blocked work

If a Story is blocked, do not leave it in In Progress without flagging it. Add a comment explaining the blocker, tag the relevant person, and use the Flagged option (the flag icon in Jira Cloud) to mark it visually on the board.

JQL & Filters

JQL (Jira Query Language) is a simple text-based filter syntax. You don't need to memorize it — a few core patterns cover most daily use cases.

Access JQL

In the board or backlog, click Filters > Advanced issue search, then switch to the JQL editor tab.

Core queries for ERM

All tickets currently assigned to you:

project = ERM AND assignee = currentUser() AND statusCategory != Done

All Stories In Progress across the team:

project = ERM AND issuetype = Story AND status = "In Progress"

All open work under a specific Epic:

project = ERM AND "Epic Link" = ERM-001 AND statusCategory != Done

Items with a due date in the next 14 days:

project = ERM AND due <= 14d AND statusCategory != Done

Saving a filter

Run your JQL query and confirm it returns the right results.
Click Save as at the top of the search page.
Give the filter a descriptive name (e.g. "My Open ERM Stories").
To share: open the filter, click Details, then set permissions to your team or project.

Team Norms

Ticket ownership

The Assignee is responsible for keeping their own ticket statuses current. Do not rely on someone else to move your tickets. Status should reflect where work actually stands today, not where it stood last week.

Description and acceptance criteria

Every Story must have a Description and Acceptance Criteria filled out before it moves to In Progress. A blank description is not acceptable — if a ticket lacks context, the Assignee is responsible for adding it before starting work.

All Stories belong to a Feature

Orphan Stories — Stories not linked to a Feature and Epic — create reporting gaps and make it impossible to understand workload at a program level. If you cannot identify a parent Feature, flag it rather than leaving the Story unlinked.

One assignee per Story

If work is genuinely shared, create separate Stories and link them. A ticket with no clear owner is a ticket that will not get done.

No story points or estimation

We do not use story points. Duration is expressed through Start Date and Target End Date. Do not estimate in points even if Jira prompts you to.

Comments over DMs

If a conversation about a ticket happens, add a summary comment to the ticket. This creates a traceable history and avoids information loss when people are out.
